## Why the week is void anyway

1. **Zero-coverage binaries since 09-21 06:13.** `nm` shows
   `__sanitizer_cov*` symbols in **none** of the 14 release binaries — the
   09-21 restart built with a plain (non-`cargo-fuzz`) release profile. The
   week-2 td_api_json chunk announces it in the log itself: `Failed to find
   function __sanitizer_acquire_crash_state` + `no interesting inputs` +
   corpus collapsed to 1 file at ~3.2M exec/s (no feedback, no crash
   detection). **Nothing since 09-21 06:14 counts toward S78.**
2. **The driver has been stuck since ~11 minutes into that chunk.** The
   uninstrumented td_api_json process went silent at ~2^31 execs; bash blocks
   on it (no `rc=` line ever followed), so no later target ran. The 09-22 and
   09-23 day-checks misread the hang as "actively fuzzing" (process-existence
   check). By 10:46 09-23 the driver and child are **gone entirely** — the
   week is stopped, not paused.
3. **Three targets were vacuous all week.** mtproto_packet / json_value /
   binlog_event show frozen coverage — e.g. mtproto_packet: cov 73 constant,
   **0 new units over 639M execs** (2120 PCs, 9 tiny seeds; the format gate
   rejects everything random). They need valid-format seed corpora before
   their minutes mean anything.
4. **Never validly fuzzed:** user_log_event, user_full, secret_chat,
   emoji_status, updates_container (binaries only existed from 09-21, already
   void), message_content (binary still missing from the release dir),

5. Best real clean windows: tl_scheme_text + transport_frame instrumented and
   finding-free ~09-15 → 09-20 (~5 days); td_api_json/app_config/simple_config

## Addendum — restart executed (2026-09-23, same day)

The restart recipe above was executed on the gate box (192.168.0.30,
work area `~/tdrs-gates/td-rs-trackj`), and the execution surfaced two real
client bugs beyond this audit's static analysis — both fixed on master with
regression tests:

1. `message_input` did not compile: the M.22 ReplyMarkup unification moved
   the type to `crate::reply_markup` and renamed the intake to
   `get_reply_markup_from_td_api`; the target still referenced the old
   `messages_manager::ReplyMarkup::from_td_api`. `fuzz/` is excluded from
   the workspace, so no workspace gate could see it — exactly the blind
   spot that produced the 09-21 phantom week. Fixed (the intake fn is now
   `pub`, matching the module's other converters), and the target was never
   built before, confirming it had never been fuzzed.
2. The restart's 60-second smokes exposed two client bugs that only fire on
   the binding surface: `td_create_client_id` was lazy (a bare receive
   never yields the startup `updateAuthorizationState`; the C++ creates the
   Td eagerly — see `conformance/bindings/README.md`), and the
   close-notification erase could deadlock on the `MultiImpl` teardown.
   Both fixed; the S81 python example now runs the Rust `.so` end to end.

3. **The 60-second smoke of `message_content` — fuzzed for the first time
   ever — found a real out-of-memory** (`oom-bf05eca0`, 17 bytes):
   `FormattedText::parse` (message_entity.rs) read the entity count and
   ran `Vec::with_capacity(len)` with only a negative check — a hostile
   count of ~2^27 entities reserved 32 GB (`malloc(34359787584)`,
   ASan-symbolized to message_entity.rs:577 through
   `parse_message_content` → `parse_formatted_text`). The C++ gates the
   count against `get_left_len()` before allocating (tl_helpers.h:170);
   the gate now mirrors that here, and the artifact replays as a clean
   reject. This is the same bug class M.4.17 fixed for the UserManager
   blob readers — the message plane had the same hole.

What the restart shipped:
